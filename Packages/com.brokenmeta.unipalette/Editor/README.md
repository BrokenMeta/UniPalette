# Editor architecture

The package is being organized into layers incrementally. One Editor assembly still contains all layers.

| Folder / namespace suffix | Responsibility | Main types |
| --- | --- | --- |
| Host | EditorWindow entry point, composition/lifetime, Editor notifications and close-before-execution | UniPaletteWindow |
| Presentation | Visual tree, recycled rows, input routing, browser formatting, session-to-view coordination and focus | PaletteView, PalettePresenter, BrowserPresentation, PaletteRow, UI assets |
| Application | Palette workflow, browser transitions, query/selection, history and source contract | PaletteSession, PaletteBrowser, ContextBrowser, CommandBrowser, PaletteHistory, ICommandSource, IContextSource, IContextSelection |
| Lifetime | Synchronous notifications and owned subscription handles | Signal, Subscription, SubscriptionScope |
| Model | Items, context identity and relationships | PaletteItem, ContextItem, asset/scene/root contexts, menu commands/categories |
| Services | Unity data access, menu discovery and native dispatch | UnityContexts, UnityContextSource, UnityContextSelection, EditorContext, MenuCommands, NativeExecution |

Internal namespaces follow BrokenMeta.UniPalette.Editor plus the folder name. The public UniPaletteWindow remains in BrokenMeta.UniPalette.Editor to preserve its full type identity for saved Editor layouts and external references.

PaletteSession is the former PaletteState: it coordinates operations as well as holding transient data. The window owns its command source and creates a UnityContextSelection shared by the session, command discovery and native preparation. The session borrows IContextSelection and the source, and unsubscribes from the source on disposal. Context confirmation happens before requesting commands. UnityContextSelection uses context visitor dispatch to create EditorContext bindings: these own Selection synchronization/matching, live target validation, scene capture and root preparation. NativeExecution retains a binding and captured target/scene through close, focus and dispatch; it never repairs Selection during execution. These services and bindings own no disposable resources. Browser objects represent immutable navigation levels retained in history. ContextBrowser borrows IContextSource, preserves that dependency when opening nested contexts and filters its results without referencing Unity services or inspecting context types. The host provides UnityContextSource, which resolves live roots and delegates child enumeration to context items. Tests provide their own source through the same required constructor contract; PaletteSession has no fixture-root parameter. The context source owns no disposable resources. Model items describe identity/relationships; PaletteView owns actual App UI elements and callbacks. PalettePresenter borrows the view/session, subscribes through methods returning IDisposable and maps input to session actions and rendering. Each consumer owns its subscription handles: the presenter groups them in SubscriptionScope, the session stores its command-source handle, and the window/view group their Editor/UI registrations. Disposal is idempotent and stops callbacks retained in a notification snapshot. Publishers keep private synchronous signals, reject subscriptions after disposal and release listeners on disposal. Temporary ListView selection-handler suppression remains local to rebinding; no callback reconnects after view disposal. No external subscription package or global event registry is involved. The host creates an ordinary BrowserPresentationSelector for each presenter and injects it through the existing IPaletteBrowserVisitor<BrowserPresentation> contract. The selector owns its two formatting instances; there is no global formatting instance or static factory. Formatting and PaletteRow data live in Presentation; Application does not reference them. These formatting objects own no disposable resources. The host disposes the presenter before the view/session/source. Host callbacks provide close, native execution and acknowledgement of the current Editor Selection before rendering.

## Remaining stages

This layout makes current responsibilities visible; strict dependency separation is not complete. Context models still read Unity data for display, validity, relationships and browsing, but no longer change or inspect Selection or prepare native execution. CommandBrowser opens categories and forwards menu leaves through the session; NativeExecution owns relevance and preparation checks at the host boundary. Navigation locations, search aliases and application error messages remain in Application. The host still watches Editor state, validates native execution and closes before dispatch.

Next stages can separate remaining Unity data reads from model descriptions when a concrete use case requires it. Adding another browser requires its visitor dispatch and corresponding presentation selection, keeping the supported browser kinds explicit without runtime type switches in the view. No additional assembly definitions, service registry or MVVM framework are required for these stages.
